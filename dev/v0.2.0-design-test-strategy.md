# v0.2.0 設計: テスト戦略

作成日: 2026-08-30  
最終改訂日: 2026-08-30  
対象範囲: v0.2.0以降  
ステータス: 方針確定  
関連文書: [CI](./v0.2.0-design-ci-pipeline.md) / [fixture](./v0.2.0-design-test-data-generator.md) / [E2E](./v0.2.0-design-e2e-ui-testing.md) / [リリース工程](./v0.2.0-design-release-process.md)

## 1. 目的

現在のRustテスト203件を維持しつつ、Tauri command契約、TS、UI、移行・復旧の空白を埋める。テスト件数やカバレッジ率を増やすこと自体ではなく、Security不変条件と利用者の主要シナリオを継続的に守ることを目的とする。

## 2. テスト層

| 層 | 主対象 | 実行 |
|---|---|---|
| Rust unit | eligibility、normalization、policy、settings、配置純関数 | ローカル+CI |
| Rust integration | SQLite migration、記録→集計、CSV、backup/restore | ローカル+CI |
| TS unit/DOM | format、bucket、router、dirty state、error表示 | ローカル+CI |
| Tauri E2E smoke | 起動、主要画面、設定、未保存ガード | リリース必須。push/nightlyは実測後判断 |
| Windows実機 | LL hook、Layered Window、UIA、UAC、MSIX | リリース前 |

## 3. トレーサビリティ

各reqの受入条件へIDを付け、次を記録する。

| 要件ID | 自動テストID | 手動受入ID | 未自動化理由 |
|---|---|---|---|

「自動化率50%/70%」のような分母不明の目標は使わない。主要シナリオが未検証なら、テスト件数が多くてもリリース不可とする。

## 4. fixture

- D05の`empty` / `light` / `boundary`を使う。
- 実行ごとの新規一時ディレクトリを使う。
- 本番DB、通常検証DB、通常設定ディレクトリを開かない。
- E2E設定の欠落・誤記時はDB初期化前に失敗する。
- 100万件fixtureは性能上の具体的課題がある場合だけ作る。

## 5. Securityリリースゲート

次は数値カバレッジに関係なく必須である。

1. 記録禁止対象の修飾なし英数記号入力がDB、Realtime Log、CSVへ入らない。
2. Security GateがOverlay、DB、Realtime Logより前に動く。
3. password/credential/unknown/elevated境界でFail Closedとなる。
4. Preview、key search、overlay退避クリックが実データ経路へ入らない。
5. Local/Elevatedの重複を二重記録しない。
6. 設定migration/import/backup復元後もKeyPolicy sanitizeが働く。
7. E2E/testdataが本番データへ触れない。

新しい入力経路、import、Tauri commandを追加する場合、該当するSecurityテストを同じフェーズで追加する。

## 6. カバレッジ

- Rustは`cargo-llvm-cov`、TSはVitest coverage providerでレポート生成を検討する。
- v0.2.0では監視指標とし、未達だけでCIを失敗させない。
- Security moduleを数値ゲートにする場合は、対象ファイル、line/branch/function、除外、baselineをreqで確定する。
- 低い値を増やすためだけの意味の薄いテストを追加しない。

## 7. 性能

通常リリースでは、現実的なlight fixtureと既存利用者DBで退行を確認する。次の閾値は実測baselineを作ってから設定する。

- 起動からUI表示
- dashboard/ranking表示
- CSV出力
- idle CPU
- 入力からOverlay表示

共有CI runnerの単発時間を厳格な失敗条件にしない。回帰傾向と専用Windows実機の複数回測定で判断する。

## 8. 手動受入

| 項目 | 現時点の理由 |
|---|---|
| 実LL hook入力 | foregroundと実デバイスの再現が必要 |
| Layered Window、click-through、DPI、複数monitor | DOM E2E対象外 |
| UIA password、secure desktop、UAC | 実アプリと権限境界が必要 |
| elevated helper | UAC対話が必要 |
| MSIX install/uninstall/StartupTask/WebView2 | クリーンVMが必要 |

専用VM等で安定再現できるようになれば自動化対象へ移す。

## 9. 実行タイミング

| タイミング | 内容 |
|---|---|
| 開発中 | 変更パッケージ/画面のunit・integration |
| フェーズ完了 | fmt/clippy、関連全テスト、必要な実機スモーク |
| PR/push | Rust、TS、UI build、静的ゲート |
| リリース前 | CI全量、E2E smoke、旧版migration、Windows実機受入 |
| Store提出前 | MSIX clean VM、WACK、移行/復旧、StartupTask |

## 10. 完了判定

- 対象reqの全受入条件が自動または手動テストへ対応している。
- Securityリリースゲートが全通過している。
- 未実施の実機項目が明示されている。
- fixtureとE2Eが通常データへ触れていない。
- 既知P0/P1不具合がない。
