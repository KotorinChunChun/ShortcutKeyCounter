## 1. ツール選定

Tauri公式が現在推奨する`@wdio/tauri-service` + WebdriverIOを第一候補とする。embedded providerをまず試し、成立しない場合だけexternal `tauri-driver`へ切り替える。

公式参照: [Tauri WebDriver](https://v2.tauri.app/develop/tests/webdriver/)

Vitest + jsdomはrendererの純関数・DOM状態、WDIOは実Tauri起動とIPC/永続化を担当する。

## 2. 最重要: Fail ClosedのE2E起動

E2E用buildは`e2e-test-mode` featureを付ける。通常release/MSIX/ZIPにこのfeatureを入れない。

起動時に次をすべて満たさない場合、UI・capture・DB初期化より前に非0終了する。

- `SKC_E2E_MODE=1`
- `SKC_E2E_DATA_DIR`が絶対path
- data dirがD05生成のmarkerを持つ
- canonical pathが許可された一時root配下
- DB名が固定のE2E名

未設定、未知値、検証失敗時にProductionへ戻らない。

## 3. 通常版との分離

- DB、JSON、ログ、CSV出力はすべてE2E data dir配下。
- 単一インスタンスMutex/pipe名へE2E実行IDを含める。
- auto-start、elevated helper、通常trayの外部状態変更を無効にする。
- E2Eで起動したPIDをrunnerが保持し、そのPIDだけを終了する。
- ユーザーが通常版を起動中でも干渉しない。

環境変数はテスト用pathの選択だけに使い、任意の本番pathは受け付けない。

## 4. v0.2.0スコープ

### スパイク

- D05 light fixtureでアプリを起動する。
- dashboardがactiveになることを確認する。
- 終了後に起動PIDと一時ディレクトリを回収する。

### P1シナリオ

1. empty fixtureで起動し、空状態が表示される。
2. light fixtureでdashboardの24時間bucketを表示する。
3. 設定画面を開き、保存可能な設定を変更する。
4. key-mappingをdirtyにし、画面移動が未保存ガードで止まる。
5. 保存または取消後に移動できる。

全11画面、CSV実出力、再起動後永続化、性能計測はP2とする。

## 5. UI Unit

- `api.ts`をmockし、Tauri globalへ直接依存しない。
- router、dirty state、error toast、format、bucketをVitestで検証する。
- DOM断片は必要最小限にし、`index.html`全体の複製を避ける。

## 6. 手動受入に残す項目

| 項目 | 理由 |
|---|---|
| 実キーボード/マウスLL hook | hosted runnerで信頼できる実入力・foregroundを保証できない |
| Layered Window実描画、click-through、DPI、複数monitor | WebView DOM外 |
| UIA password判定、UAC、secure desktop | 実アプリ・権限境界が必要 |
| elevated Capture helper | 対話的UACが必要 |
| MSIX install/uninstall/StartupTask | D07のクリーンVM受入 |

「自動化不能」と永久決定せず、専用VM等で安定して再現できるようになれば見直す。

## 7. CI

- v0.2.0ではローカル/専用Windowsでのスモークをリリース必須にする。
- pushごとの実行はスパイクで所要時間とflakinessを測って決める。
- nightly化する場合、アプリlog、WDIO log、fixture reportをartifact化する。
- 失敗時に通常DB/通常data dirへアクセスしていないことをログで確認できるようにする。

## 8. 完了条件

- E2E設定欠落時にDBを開く前に失敗するテストがある。
- 通常版起動中でも専用mutex/data dirでスモークが通る。
- P1の5シナリオが再現可能に通る。
- cleanupが起動PID以外を終了しない。
- 手動受入との要件ID対応表がある。
